# Architecture

Last updated: 2026-10-26. Describes the planned structure; what already exists
in the code is marked as such.

## Overview

```
┌──────────────────────────────┐      invoke()       ┌─────────────────────────────┐
│ Frontend (React + TS, Vite)  │ ──────────────────▶ │ Rust backend (Tauri 2)      │
│ search, filters, lists       │ ◀────────────────── │ commands, config, sources,  │
│                              │                     │ I/O                         │
└──────────────────────────────┘     JSON (serde)    └──────────────┬──────────────┘
                                                                     │ HTTPS
                                                     ┌───────────────┴──────────────┐
                                                     │ CurseForge API (then Wago,   │
                                                     │ WoWInterface, GitHub)        │
                                                     └──────────────────────────────┘
```

Rule: everything that touches the network, the disk and keys lives in the backend. The frontend
shows data and calls commands; it does not know the API key.

## Backend modules (`src-tauri/src/`)

| --- | --- | --- |
| `config` | Reads `CURSEFORGE_API_KEY` from the environment / `.env` | Exists |

| `installations` | Finds and manages WoW installations, also inside Wine prefixes | Exists (manual addition and validation; automatic discovery is in `discovery`) |
| `discovery` | Automatic discovery of installations (`discover_installations`): one function per platform builds the candidate `World of Warcraft` folders (Windows: the registry's `InstallPath`, D30, then `World of Warcraft`, `Program Files (x86)`, `Program Files` and `Games` on every drive from C to Z; macOS: `/Applications` and `Applications` in the home folder asked of Tauri; Linux: `World of Warcraft` under `drive_c/Program Files (x86)` and `drive_c/Program Files` of every Wine prefix in the home folder, that is `.wine`, the children of `Games` (Lutris), the bottles of native and Flatpak Bottles and the `pfx` folders of `steamapps/compatdata` (Steam/Proton), at fixed levels, with names read case-insensitively and without reading the Lutris, Bottles or Steam configurations); a common function reads only the candidates and their direct children, keeps the `_<flavor>_` folders valid for `installations::validate` that still contain the game (`.flavor.info`, a `Wow*.exe` or an `*.app` bundle: the folder left behind by an uninstall is not suggested), without duplicates (same id) and without those already in `installations.json`. Returns `path`, `flavor`, `name` and `origin`; it only suggests, writes nothing, and finding nothing is not an error | Exists (backend; interface to do, issue #89) |
| `addons::toc` | Reads the `.toc` files in `Interface/AddOns` (title, version, `## Interface`) and picks the right `.toc` for the installation's flavor | Exists |
| `addons::scan` | Reads the folders of `Interface/AddOns` and their `.toc`, without modifying anything | Exists |
| `addon_import` | Import of a string (issue #134). `preview_import` reports for each project `new`, `installed` or `notDownloadable` (CurseForge without a key or with `allowModDistribution` false and without a GitHub `sourceUrl`: a blocked project with a GitHub repository counts as installable and the installation tries the mirror of D34, issue #179; Tukui project not listed, sources not yet supported; GitHub projects count as installable without reading the release, so as not to spend the request limit), the invalid entries and the folders *Replace all* would remove. `import_addons` (under `InstallLock`) installs the missing ones in two phases (issue #180), in groups of 24 entries: first it resolves and downloads without touching the disk, at most 6 entries at once (`parallel::DOWNLOADS_AT_ONCE`) — CurseForge one dependency level at a time with one `get_mods` and one `POST /v1/mods/files` per level, each project only once, GitHub mirror included (`install_new::prefetch`); Tukui and GitHub with `download_new` —; then it installs one entry at a time in list order with the existing flow on the already downloaded zips (CurseForge with dependencies, mirror and the entry's forced version saved as an override); outcomes and rules stay those of one-at-a-time installation; then with `replace`, if at least one installation succeeded or everything was already present, it rereads the disk and removes only the confirmed folders (`confirmedRemovals`) that no imported project claims, either directly or as a dependency declared in the `.toc` of a folder that stays. No backup (the user's choice); deletion is `install::remove_folder`, a single valid component inside `AddOns`, links are removed without following them; `WTF` and SavedVariables are not touched. Removed folders leave the records and the fingerprint cache | Exists (interface: "Import / export" section of Options, issue #135) |
| `addon_remove` | Removal of one or more addons (`remove_addons`, issue #147): for each requested folder `install::remove_folder` (a single valid component inside `AddOns`, links are removed without following them, a file that is not a folder stays) and a `removed` or `error` outcome with the message, without stopping at the first one that fails; a repeated (identical) name counts once. Removed folders leave the records (`forget_folders`) and the fingerprint cache; a registry that does not update becomes a warning (`warning`). No backup (the user's choice); `WTF` and SavedVariables are not touched. Holds `InstallLock` | Exists (backend; in the Installed tab from the context menu, issue #149) |
| `addon_list` | Import/export string of an installation's addons (issue #133): `WOWDON1:` followed by unpadded base64url (written in the module) of a JSON `{v, flavor, addons: [{source, key, name, versionType?}]}`. `decode` rejects unknown prefix or version, malformed base64 or JSON, texts over 64 KiB or with more than 1,000 entries, and skips invalid entries while reporting them; `export_list` derives the list from the results of `refresh_addons` (one project per entry, with the forced version) plus the registered projects the check does not recognise, and names the folders without a project. Command `export_addons` | Exists |
| `addons::cache` | In-memory cache of fingerprints per folder (state managed by Tauri, issue #125): a fingerprint is reused if the paths, sizes and modification dates of all the folder's files are the same as at the last computation; folders written by the app (update, installation, zip) leave the cache, "Reload addons" (`refresh_addons` with `force`) recomputes the whole installation, vanished folders leave at the next scan. Nothing on disk | Exists |
| `addons::fingerprint` | Computes CurseForge fingerprints (MurmurHash2 seed 1 without whitespace, on the files included by `.toc` and `.xml`) to recognise installed addons; the hash is computed in streaming and the files read are not copied. `addons::scan` reads folders in parallel with the standard library's threads (issue #124) | Exists |
| `sources` | Common `Source` trait for the sources (D12): `check` matches the offered folders and evaluates updates, `update` downloads, replaces the folders and registers the record with the source's distribution rules. Projects are identified with `ProjectKey` (`source` + `key`, the id in the source as a string); `Project`, `AddonUpdate` and `UpdateOutcome` carry `source` and `key`, and `id`/`modId` stay the CurseForge id (`0` for the other sources). Planned sources: `curseforge`, `tukui`, `wowinterface`, `github` (D31) | Exists (CurseForge as `updates::CurseForgeSource`, then Tukui, WoWInterface and GitHub) |
| `sources::curseforge` | Client for `https://api.curseforge.com/v1` with the `x-api-key` header: fingerprints, mods, game version types, search (`/v1/mods/search`), categories (`/v1/categories`), description (`/v1/mods/{modId}/description`) and a mod's files with their dependencies (`/v1/mods/{modId}/files`) | Exists |
| `sources::http` | The HTTP layer common to the sources: responses, `TransportError` and reading with a limit (`read_limited`), also used by the CurseForge client. For the free sources, the keyless transport `PublicTransport`: `GET` of JSON responses (at most `MAX_JSON_BYTES`, 4 MiB) and downloads with the `MAX_DOWNLOAD_BYTES` limit, redirects followed only towards the source's domains (`is_allowed_url`: `https`, without credentials or port, the domain or one of its subdomains; the same rule applies to CurseForge downloads) | Exists |
| `sources::github` | GitHub Releases source (D31, issue #108), without a token: only projects with a `github` record (`id` = `owner/repo`, validated before composing the URL), never automatic matching of addons installed by hand. The check reads the release **without the API** (D37, issue #179): the tag from the `Location` header of `https://github.com/{owner}/{repo}/releases/latest`, with a transport request that does not follow redirects (`PublicTransport::get_redirect`, a second `reqwest` client with `redirect::Policy::none()`); the `Location` must be `https://github.com/{owner}/{repo}/releases/tag/{tag}` of the same repository, a `releases/latest` of a moved repository is followed once, a 404 is "no release". When the zip is needed, the `release.json` and the zip are read from `https://github.com/{owner}/{repo}/releases/download/{tag}/…`. Only a release without `release.json` (404) reads `GET https://api.github.com/repos/{owner}/{repo}/releases/latest` (`Accept: application/vnd.github+json`, the app's `User-Agent`) for the assets, and the tag must be the same. Each read is made once per run, even when it answers with an error, and a release read (from the site or from the API) is valid for ten minutes, also for later commands (a shared cache: every Reload redoes the check); the installed version is the record's tag and a different tag is an update. Without the API the release date stays empty. The zip: with the packager's `release.json`, the entry whose `metadata` contains the packager's flavor for the game (`_retail_` → `mainline`, `_classic_era_` → `classic`, `_forever_` and `_classic_beta_` → `forever`, `_anniversary_` → `bcc`, `_classic_` → `mists`, derived from the families of `toc::toc_suffixes`; a family without an entry chooses no file), preferring `nolib: false` (no entry for the game is an error of the folder); without `release.json`, the only `.zip` that does not end in `-nolib.zip`; otherwise the project is "site only" (`allowModDistribution` false). The limit of 60 requests an hour applies only to the API fallback: a 403/429 response with `x-ratelimit-remaining: 0` becomes an error with the UTC time of `x-ratelimit-reset` and stops later requests to the API (not those to the site), including those of other commands, until the reset. In an import preview an id that is not `owner/repo` is not installable. Errors are per project and do not touch the other folders. Assets are downloaded only from `github.com` and `githubusercontent.com` (also in redirects), with the common limit and extraction; folders the new zip no longer has are removed and the record takes the new tag | Exists |
| `sources::github_mirror` | GitHub mirror of blocked CurseForge projects (D34, issue #162). `resolve(github, project, file, flavor)` receives the CurseForge project, the file `pick_file` chooses for the installation and the game's flavor, and returns `Mirror { repo, tag, asset }` or `Unavailable { reason }`. A project with `allowModDistribution: true` (`NotBlocked`) or without a GitHub `sourceUrl` (`NoGithubSource`) makes no requests; the repository comes only from `links.sourceUrl` (`github_repo`, with the parsing of `install_link::parse_link`: `www`, `.git`, trailing slash and subpaths, never another host). The release is read with `GithubSource::latest_release` (without the API, D37; the same ten-minute cache, typed error `ReleaseError`: limit, missing release, other) and the zip with `GithubSource::choose_zip` (typed error `ChoiceError`: no file for the game, limit of the API read only for a release without `release.json`, which becomes `RateLimited`, or unreadable `release.json`, which becomes `Failed`). The same-version rule is the pure function `same_version`: a zip with the same name as the CurseForge file, or the tag without `v` as a whole version in the `fileName` or in the `displayName` (delimited by the start or `-`, `_`, space, also followed by `v`, and by the end, `_`, space, `.zip` or a `-` not followed by a digit, so the Alpha `4.18.3.1-1-g…` does not count as `4.18.3.1`). The English reasons are distinct: no GitHub repository, release not found, no zip for the game, different release (with the two versions), GitHub limit (with the unlock time), network error . The `MirrorSource` trait (implemented by `GithubSource`) gives `CurseForgeSource` `resolve` and the zip download; `install` downloads the zip with the rules of `github.rs` and extracts it with `updates::install_bytes`, and the CurseForge record is written by the caller (`updates::record_curseforge`) | Exists (used by updates and reinstallation, issue #163, and by installation from Search, issue #164, which reuses `resolve` and `install` and writes the CurseForge record with the `install_addon` callback) |
| `sources::tukui` | Tukui source (D31) on `https://api.tukui.org/v1/addons` (ElvUI `-2`, Tukui `-1`), read once per check and reused by the update: an addon is installed if all its `directories` are in `AddOns` (case-insensitively) or if it has a record; the installed version is the record's, otherwise `## Version` of the first folder's `.toc`, and a version different from `version` (not counting a leading `v`: ElvUI's `.toc` writes `v16.00`) is an update. It applies to the installation if `patch` contains a version of its game or if the installed `.toc` declares it (`patch` does not list WoW Forever, which the zip supports), otherwise the folder reports an error; the zip is downloaded only from `tukui.org` (the URL contains a token, never in logs), the project's folders the new zip no longer has are removed, and it is registered with the version as `file`; a list entry that cannot be read is skipped without removing the others | Exists |
| `sources::wowinterface` | WoWInterface source (D31, issue #107) on the public MMOUI API, without a key: `GET https://api.mmoui.com/v4/game/WOW/filedetails/{id}.json`, with several comma-separated ids in a single request (at most 50 per request; ids that do not exist are missing from the array, and if none exists the response is `404` with `{"ERROR": …}`, treated as an empty list). The full `filelist.json` is never downloaded, and with no folders to check no request starts. A folder belongs to the project if a `wowinterface` record names it, otherwise if the flavor's `.toc` declares `## X-WoWI-ID`; several folders with the same id are a single project, and folders already claimed by CurseForge do not arrive (D33). The installed version is the record's, otherwise `## Version` of the `.toc`; a version different from `version` (not counting a leading `v`) is an update. An id WoWInterface does not know does not claim the folder. The check's responses are reused for the update; the zip is downloaded from `downloadUri` only on `wowinterface.com`/`mmoui.com` with the common limit and extraction, the project's folders the new zip no longer has are removed, and it is registered with the version as `file`. Network errors and unreadable responses are errors of this source only | Exists |
| `catalog` | Search in the CurseForge catalogue for an installation (`search_catalog`): 50 results per page, the installation's game version or one known to the app, sort orders `popularity`/`lastUpdated`/`name`/`totalDownloads` translated into `sortField` 2/3/4/6, beyond the API's 10,000 results an empty page with the real count; addons without a Release file for the searched version are removed from the page (the installation could not install them: `gameVersionTypeId` also includes Beta-only projects), and the page reports how many results it read (`fetched`) and how many it hid (`hidden`), so pagination does not stop on a page emptied by the filter (issue #140); with the "Use beta files when there is no release" option (`betaWhenNoRelease` in `settings.json`, issue #141) an addon with only a Beta for the version stays, with the Beta file (`releaseType` 2) and the "Install beta" action. The file choice rule is a single one, `sources::curseforge::pick_file`, for search, detail, installation (with dependencies) and update: the most recent Release, otherwise the most recent Beta only with the option, never Alpha; with the option off an update that would be Beta only has the `betaOnly` status; categories by name without the classes (`list_categories`). The `installed` flag (a record in `installed-addons.json` with a folder still present, or `## X-Curse-Project-ID` in the `.toc`) does not call the API and is the "already installed" rule also for installing a new addon. An addon's detail (`addon_detail`): the search fields, the description converted to plain text in the backend (no author HTML in the webview; the frontend shows it **only as text**, never with `innerHTML` or `dangerouslySetInnerHTML`, because decoded entities can contain `<` and `>`), the gallery images (`screenshots`: `title`, `description`, `thumbnailUrl`, `url`, in the API's order, from the same `get_mod` with no extra requests; only those with an `https` `url` on `forgecdn.net` or one of its subdomains, without credentials or port, pass, with the thumbnail falling back to `url` if it is missing or not on the CDN; title and caption as plain text, empty if missing; the backend does not download the images, the frontend loads them with `<img src>` like the logo, issue #167), up to 20 Release and Beta files from the most recent (first and, beyond 50 files, last page of `/files`, sorted by id: the order of the response does not matter) and the required dependencies (`relationType = 3`) of the latest Release, the one in `latestFilesIndexes` for the version (read with `get_file` if it is not among the files read) or otherwise the most recent among all the files read, with names read from a single `get_mods`; without an explicit version the project's forced one applies, then the installation's | Exists (backend; the Search tab is to do) |
| `updates` | Scans the installation and offers the folders to the sources in the order of D33 (`check_updates`): a folder named by a record in `installed-addons.json` goes only to the record's source (a folder in the records of several sources to none in particular), the others to every source that has not claimed them yet, CurseForge first; only a source that gives the folder a project claims it (an error on a folder is held back and shown if no source recognises it); a source that fails does not stop the others and the folders that were offered to it report its error, while if all fail the check fails; an unreadable `installed-addons.json` does not block the check. Without `CURSEFORGE_API_KEY` check and update do not fail right away (issue #123): CurseForge fails like any source, the free sources check and update their folders, the others report the missing key and a CurseForge project requested for update has an error outcome with the same reason. `update_addons` receives `modIds` (CurseForge) and `projects` (`{source, key}` of any source), redoes the check and passes each project to its source. With `reinstall` (optional, false by default; issue #148) the same cycle also redownloads a project that is already up to date: CurseForge installs the file the single `pick_file` rule chooses (Release, then Beta with the option, never Alpha) even if it is the installed one, but never a file older than the installed one (no silent rollbacks to an earlier version), Tukui and WoWInterface the listed version, GitHub the file of the installed release (chosen from `release.json` only at reinstall time); `allowModDistribution`, the missing download link, the `install-progress` event, the registry and the fingerprint cache remain, and a project no folder ties to a source gives `skipped` "Not linked to a source: cannot reinstall.". For CurseForge it matches addons to projects with fingerprints, finds the most recent Release file for the game version, then downloads the file and replaces the folders; a folder of the installed file missing from the new zip is removed only if it is still on disk with the fingerprint of the installed module, is not a module of another recognised project and no other addon declares it among the dependencies in its `.toc`. A blocked project (`allowModDistribution` other than `true`, D13) uses the GitHub mirror (D34, issue #163): the check computes it only for the `updateAvailable` status (once per project and file), after the check of all sources (`Source::finish`), so the releases of registered GitHub projects are read first and the mirrors do not consume the limit of 60 requests an hour; each blocked project with an update costs the `releases/latest` redirect per release every ten minutes (the shared cache of `GithubSource`) plus, at every check, the `release.json` from `github.com`, neither of the two within the API limit (D37; the API only for a release without `release.json`), and exposes it in `AddonUpdate` as `githubMirror` (`{ repo, tag }` or `null`) and `githubMirrorReason` (text or `null`); update and reinstallation reread the file and the project, recompute the mirror (the release is already in the cache) and download the GitHub zip, writing the **CurseForge** record with the id of the matching file ("Installed from GitHub (<owner>/<repo> <tag>): CurseForge blocks third-party downloads."); without a mirror the outcome is `skipped` with the reason (`error` for a network error) | Exists (Retail, Classic Era, Classic, Anniversary, WoW Forever; ids verified against the API) |
| `install` | Safe extraction of the zip into a staging folder next to `AddOns` (no absolute paths, `..`, drives or symbolic links; limits on entries and size) and replacement of the folders with rollback on error (D26) | Exists (used by `update_addons` and `install_addon`) |
| `updates::refresh_addons` | Addon list and update statuses from a single scan (command `refresh_addons`, issue #126): "Reload addons" and the rereads after an update, an installation from Search or from a zip use it instead of `list_addons` plus `check_updates`; a failed check, or connections that cannot be prepared, leave the list with `checkError`. The tab's first load stays `list_addons` followed by the check, to show the list before the network | Exists |
| `install_local` | Installation of a zip downloaded by hand by the user (`install_zip`, D32): accepts only a `.zip` file within the download size limit, extracts it with the rules of `install`, rejects the whole zip if a top-level folder does not have a `.toc` with its name (`<Folder>.toc`, `<Folder>_<suffix>.toc` or `<Folder>-<suffix>.toc`, case-insensitively) and replaces folders with the same name without confirmation; returns the installed folders and the replaced ones and holds `InstallLock`. It writes no records: the addon is then recognised by its fingerprint; the command does however remove whole records (of any source) that name a folder written by the zip, replaced or recreated (`InstalledAddonsStore::forget_folders`, issue #117), and if it cannot the outcome carries a warning (`warning`) instead of failing | Exists (interface: dragging a file onto the window with the `ZipDrop` layer and the "Install from zip…" button in the Installed tab) |
| `install_link` | Installation from a link (issue #109). `parse_link` is a pure function on `reqwest::Url`, without network: it recognises `github.com/<owner>/<repo>` (also with `/releases`, `.git` and the like, without reserved paths such as `orgs` or `settings`), `wowinterface.com/downloads/info<ID>-<name>.html` (also `download<ID>` and `fileinfo.php?id=`) and `tukui.org/elvui` / `/tukui` (ElvUI `-2`, Tukui `-1`), with or without `www` and with `https://` implied; another host, a CurseForge link or a malformed link is a clear error. `resolve_link(installationId, url)` returns the preview (`source`, `id`, `name`, `version`, `downloadable`, `message`, `url`, `installed`) with one request to the source (`GithubSource::preview` with the same zip choice as the installation, `WowInterfaceSource::preview`, `TukuiSource::preview`; for WoWInterface the API does not state the game and every listed project counts as downloadable, for Tukui a `patch` that does not name the game becomes a warning because the installation also looks at the zip's `.toc` files). `install_from_link(installationId, source, id)` (under `InstallLock`, records of all sources read there: an unreadable registry blocks) validates the id without network, skips an already installed project (a record of the same source with a folder still in `AddOns`; for GitHub case-insensitively) without network, then installs with the source's `install_new` and a check of the folders: a folder of the zip already present that a record of another project (of any source) names, or without a record with `## X-Curse-Project-ID` in the `.toc`, makes it fail without touching the disk, as in `install_new`. It writes the source's v2 record and returns an `UpdateOutcome` (`updated` = installed) | Exists (interface: issue #110) |
| `progress` | Progress of installations and updates (issue #127): the phases `checking`, `downloading` (with `received` and, if the server declares it, `total` in bytes), `downloaded` (import only: zip ready, waiting for its turn; issue #180), `extracting` and `installing` of a project, identified by `source` + `key` with its `name`. `updates`, `install_new` and `install_local` receive a callback and do not know Tauri; the `update_addons`, `install_addon` and `install_zip` commands connect it to the `install-progress` event, with `installationId`. The download bytes come from the read loop of `sources::http::read_limited_with`; `Reporter` lets through at most about ten per second per project plus the final one. The payload contains no URLs, keys, headers or paths. A zip chosen by the user has no source (`source` null, `key` empty). The events have no final phase: a skipped or failed project can stop at `checking`, so the listener closes the progress of all projects when the command returns the outcomes, which remain the definitive answer. Without `Content-Length` the last download step also has no `total` | Exists (backend; the bar in the frontend is issue #128) |
| `tray` | Tray icon and close to tray (D35, issue #158): `create` builds the icon (app icon, tooltip "WoW-don", menu "Show WoW-don" / "Quit") in `setup` and records in `TrayStatus` whether it exists; on Linux it first asks `dlopen` whether `libayatana-appindicator3.so.1` or `libappindicator3.so.1` load (the same names as tray-icon), because without the library tray-icon panics and with `panic = "abort"` the app would close. `TrayStatus::available` is true only if the icon was created and, on Linux, if at that moment there is an `org.kde.StatusNotifierWatcher` with a registered host on the session bus (property `IsStatusNotifierHostRegistered` read with GIO, already loaded by GTK, timeout 200 ms; without a watcher the call fails, and every error counts as no): it is asked at every close and at every `get_settings`, not at startup, because with autostart the shell may register the watcher after the app. `on_window_event` intercepts `CloseRequested` of the `main` window and hides it only if `hide_on_close` (pure function: `closeToTray` read and true, icon present) says so and `hide` succeeds; `on_run_event` reopens the window on `RunEvent::Reopen` (macOS only). **Update count** (issue #202): at the end of every automatic round `show_round` rebuilds the menu with, above "Show WoW-don", a non-clickable entry "N updates available" ("1 update available" for one) and puts the same text in the tooltip ("WoW-don — N updates available"); with zero the entry disappears and the tooltip goes back to "WoW-don". The text comes from the pure function `round_summary`: N is the sum over all the round's installations of `available` minus `updated` (in `notify` the available updates, in `install` those left over, skipped or failed; excluded ones are not in `available`). Without an icon (`tray_by_id` empty) it does nothing, and menu and tooltip errors are ignored | Exists |
| `autostart` | Start with the system (D36, issue #159): registers `tauri-plugin-autostart` with the `--autostart` argument (LaunchAgent on macOS). `get_autostart` reads from the operating system whether the entry exists, `set_autostart(enabled)` writes or removes it and returns the reread state; the plugin's errors come back in English with the cause. `start_hidden` (pure function: arguments, `closeToTray`, icon available, asked last because on Linux it queries the session bus) decides whether to start in the tray; `show_main_window_unless_hidden_start`, called in `setup` after `tray::create`, shows the main window, declared invisible in `tauri.conf.json`, in the other cases | Exists |

## CurseForge APIs used

- `GET /v1/mods/search` (with `gameId = 1` for WoW): search and filters.
- `GET /v1/mods/{modId}` and `GET /v1/mods/{modId}/files` (with `gameVersionTypeId`, `index`
  and `pageSize`, at most 50; `pagination.totalCount` says whether more pages are needed, and
  `index + pageSize` stays within 10,000): details, versions and, for each file, `dependencies` (`modId`,
  `relationType`: 1 EmbeddedLibrary, 2 OptionalDependency, 3 RequiredDependency, 4 Tool,
  5 Incompatible, 6 Include).
- `GET /v1/mods/{modId}/description`: full description in HTML (`data` is a string),
  converted to text before it reaches the frontend. The text is not safe HTML: it is shown
  with React's text binding (which escapes it), never as HTML.
- `POST /v1/fingerprints/1`: recognises installed addons from the folders' fingerprints;
  each folder is matched first against `exactMatches` and, only if it is not there, against the
  file in `partialMatches` whose `modules` contain its fingerprint (as WowUp does).
- `GET /v1/games/1/version-types`: game version types (Retail, Classic, …).
- Game versions (Retail, Classic, beta) are read from the API, not written
  by hand.

Details to verify against the official documentation before implementing them: the
file normalisations for the fingerprint and the game version IDs. The
WowUp code (open source) is a good reference.

## WoW installations

The app runs on Linux, Windows and macOS (D23, D29). On macOS the client is native, without
Wine: the `_<flavor>_` folders have the same structure and the file system (APFS) usually does
not distinguish upper and lower case, like Windows. On Windows the game sits in the folder chosen
by Battle.net, usually:

```
C:\Program Files (x86)\World of Warcraft\
├── _retail_\
├── _classic_era_\
└── Data\
```

On Linux the game runs inside a Wine prefix. A real example: Battle.net on Lutris
with the prefix in `~/Games/battlenet`:

```
~/Games/battlenet/drive_c/Program Files (x86)/World of Warcraft/
├── _retail_/            # if installed
├── _classic_era_/       # if installed
├── _forever_/           # WoW Forever (product `wowf`), if installed
├── _classic_beta_/      # WoW Forever beta (product `wow_classic_beta`)
│   ├── Interface/AddOns/
│   └── WTF/
└── Data/                # shared between versions
```

Each `_<flavor>_` folder is a separate installation. The app must be able to add
installations by hand and look for them in the Wine prefixes of the home folder (`discovery`,
issue #88); prefixes in custom paths remain a manual addition.

## Window

The main window (`main`, defined in `tauri.conf.json` without `center` or a fixed position
and without `label`, hence with the default label `main`) remembers size,
position and maximised state with `tauri-plugin-window-state` (D28), registered in `lib.rs`
with only the `SIZE`, `POSITION` and `MAXIMIZED` flags and with a filter on the `main` label: a
window added in the future does not inherit the behaviour without an explicit choice;
visibility, decorations and full screen are not saved. The plugin restores the state when
the window is ready, updates it at every move and resize and writes it on exit
to `.window-state.json` inside `app_config_dir()` (D22). The saved size is that of the
non-maximised window: in 2.5.0 both the `Resized` handler and `update_state` skip
size and position when `is_maximized()` is true, so un-maximising brings back
the window as it was. If the monitor the window was on is no longer there, the saved position
is ignored (it is set only if the saved rectangle intersects one of `available_monitors()`) and
the window opens where the system puts it, on a present monitor. The frontend has no
permissions for the plugin's commands: only the backend uses it.

**Close to tray** (D35, `tray` module): with `closeToTray` on and the icon present, closing the main window hides it instead of closing the app. The plugin still updates its in-memory state on `CloseRequested`, and "Quit" from the tray calls `exit`, which emits `RunEvent::Exit` where the plugin writes the file: the state is saved even if the window was hidden. On GNOME without the AppIndicator extension the library is there but nobody shows the icon: `org.kde.StatusNotifierWatcher` is missing from the session bus (or has no registered host), so `trayAvailable` is false and the X closes. A desktop that shows only the old XEmbed tray, without a watcher, has the same outcome: a false negative that lets the X close, never a hidden window without an icon.

**Hidden start** (D36, `autostart` module): the main window is declared with `"visible": false`, so there is no flash before hiding it, and the plugin of D28 does not show it because its flags do not include `VISIBLE`; it restores size, position and maximisation on the still invisible window (on Windows tao does not call `ShowWindow` to maximise an invisible window) and `setup` shows it right after, except when the app started with `--autostart`, `closeToTray` is on and the tray icon is visible at that moment. No retries: if at login the shell has not yet registered whoever shows the icon, the window opens.

**Limit on Linux with Wayland**: the compositor does not let applications read or
set the position of their own windows, so there only the size
and the maximised state are restored; the compositor chooses the position. It is not worked around (for example
by forcing X11/XWayland): it is a choice of the protocol. On X11, on Windows and on macOS the
position is restored too.

## Security

- The key is never sent to the frontend or written to logs.
- In production the key will come from the user config (format and location from D22).
- On Windows `canonicalize` returns paths with a `\\?\` prefix, to be removed
  before showing or saving them.
- Downloaded zips are extracted into a temporary folder and it is checked that the
  paths do not leave the `AddOns` folder before moving them.
